## 1. 项目背景与定位

### 1.1 应届生求职的四大痛点

| 痛点 | 具体表现 |
|------|---------|
| **岗位认知模糊** | 打开 JD 满篇术语——"RAG""Agent""SFT"——根本看不懂这个岗位到底在做什么，更不确定自己能不能做 |
| **匹配无感** | 即使看懂了 JD，也不知道自己的经历哪条算"相关"、哪条不算，无法判断匹配程度 |
| **反馈缺失** | 投了 50 份简历没回音，不知道是简历问题还是能力问题，也无从改起 |
| **效率低下** | 每份 JD 手动比对、改简历、写求职信，一份至少 30 分钟，投不起 |

这四重痛点的本质是：**求职者缺少一个"私人职业顾问"**——能翻译 JD、读懂简历、诚实告诉你差距在哪、怎么补的人。

### 1.2 CareerMatch Agent 解决什么

> **一句话：AI Agent 求职助手——上传简历 + 粘贴 JD，3 分钟内输出匹配度报告、简历优化建议、个性化求职信、面试题预测。**

不是关键词匹配器，而是：

- **理解 JD 背后的真实需求**（"熟悉大模型" = 用过 API？微调过？还是只需要会 prompt？）
- **从招聘方视角审视简历**（这个候选人看完简历我会约面试吗？为什么不？）
- **给出可操作的下一步**（简历第 3 段改这句，准备这 5 道面试题）

### 1.3 为什么是 Agent 而不是普通 Chatbot

普通 Chatbot（把 JD+简历扔给 ChatGPT）的问题：

- 输出质量完全依赖 prompt 质量，用户不会写 prompt
- 没有结构化输出，这次 5 个维度下次 3 个，无法对比
- 无法调用外部工具（比如联网查公司背景）

**Agent 的优势**：主动规划分析路径 → 调用工具 → 校验输出 → 生成报告。不同 JD 走不同分析策略。

### 1.4 产品定位：求职作品集核心项目

这个产品本身也是我（秦俪萍）的求职作品——**证明 AI PM 能独立定义、设计、交付 AI Agent 产品**。21 天从 0 到上线。

## 3. 核心需求（用户故事）

### US-01 看懂 JD
> **作为** 应届生求职者，
> **我希望** 粘贴一份 JD 后，Agent 能用人话翻译岗位的核心要求（技术栈、经验年限、软技能），
> **以便** 我快速判断这个岗位到底在招什么人，而不是被满篇术语劝退。

**验收标准**：
- 输入一份 JD，输出 ≤ 5 行"岗位画像摘要"
- 摘要覆盖：核心职责、必备技术、加分项、团队协作方式

### US-02 诚实匹配
> **作为** 应届生求职者，
> **我希望** 上传简历后，Agent 诚实地告诉我匹配度（0-100%）以及具体在哪些维度匹配/不匹配，
> **以便** 我不浪费时间去投明显不合适的岗位，也敢投那些"差一点但能补"的。

**验收标准**：
- 输出 8 个匹配维度，每个维度标注：完全匹配 / 部分匹配 / 不匹配 + 一句证据
- 综合评分 0-100%

| # | 维度 | 关注点 |
|---|------|--------|
| 1 | **技能匹配** | 硬技能（Python、SQL、AI 概念等）是否覆盖 JD 要求 |
| 2 | **经验匹配** | 实习/项目经历是否与 JD 描述的职责对口 |
| 3 | **学历匹配** | 学历层次 + 专业方向是否符合 |
| 4 | **项目匹配** | 课程/个人项目的深度和方向是否相关 |
| 5 | **软素质** | 沟通、协作、ownership 等非技术能力 |
| 6 | **行业认知** | 对 AI 赛道、竞争格局、技术边界的理解 |
| 7 | **产品方法论** | 需求分析、用户研究、竞品分析、优先级排序等 PM 基本功 |
| 8 | **成长潜力** | 学习速度、复盘能力、从失败中提炼洞察的能力 |

### US-03 改简历
> **作为** 应届生求职者，
> **我希望** Agent 针对不匹配的维度，给出简历的具体修改建议（哪一段改什么、怎么改），
> **以便** 我能立刻动手优化简历，而不是得到一句"项目经验不够"就算了。

**验收标准**：
- 每条建议包含：定位（第几段第几行）→ 问题 → 改法 → 示例文案
- 至少输出 3 条可操作建议

### US-04 写求职信
> **作为** 应届生求职者，
> **我希望** Agent 基于匹配结果，自动生成一封个性化求职信，
> **以便** 我花 1 分钟而不是 30 分钟就能投出一份有诚意的申请。

**验收标准**：
- 求职信包含：开头（对公司的了解）、中间（我的匹配点+证据）、结尾（call to action）
- 语调可调（正式/半正式/有活力）
- 不超过 300 字

### US-05 押面试题
> **作为** 应届生求职者，
> **我希望** Agent 基于 JD 和我的简历差距，预测面试官最可能问的 5 道题，
> **以便** 我提前准备，不会在面试现场被问到"你做过 RAG 吗"时大脑空白。

**验收标准**：
- 覆盖：技术基础题 + 项目深挖题 + 行为题 + 行业认知题
- 每道题附带：面试官为什么问这个 + 参考答案要点

### 用户故事优先级

| 优先级 | 用户故事 | 理由 |
|--------|---------|------|
| **P0** | US-01 看懂 JD + US-02 诚实匹配 | 核心价值链：先看懂，再比对。MVP 必须有的最小闭环 |
| **P1** | US-03 改简历 + US-05 押面试题 | 从"知道差距"到"能行动、能面试"——投递前和面试前最刚需的两个动作 |
| **P2** | US-04 写求职信 | 锦上添花，非核心差异化，v0 可做最简单版本 |

### 4.2 模块职责

| 模块 | 负责 | 不负责 |
|------|------|--------|
| **解析层** | 把非结构化的 PDF/DOCX/粘贴文本 → 结构化 Pydantic 对象 | 不做匹配、不打分、不调用 LLM |
| **Agent 引擎** | 接收结构化数据 → 规划分析路径 → 调度工具 → 组装输出 | 不做文件解析、不直接面向用户 |
| **工具集** | 每个工具做一件事：翻译 JD 术语、匹配技能、评估公司（PMF/融资/Leader/方向）、联网搜索行业信息等 | 不跨工具调用、不做决策（由 Agent 调度） |
| **输出层** | 把 Agent 结果格式化为可读报告 | 不做分析、不修改 Agent 结果 |

### 4.3 数据流

```
用户输入（非结构化）
    → Parsers 结构化
        → Agent 规划 + 工具调用
            → Pydantic 校验
                → 报告输出（Markdown）
```

### 4.4 公司评估工具——应届生如何选公司

v0 聚焦初创公司评估（大厂 JD 信息透明，初创公司信息不对称更严重）。

| 评估维度 | 判断方法 | 数据来源 |
|----------|---------|---------|
| **PMF 状态** | 产品是否有付费用户？复购率如何？是否还在"找方向"阶段？ | 官网、36kr、企查查、产品评论区 |
| **现金流/融资** | 最近一轮融资时间、金额、轮次。超过 18 个月没融资 → 关注 | 企查查、IT 桔子、Crunchbase |
| **直属 Leader** | Leader 是否有真实项目交付经验（不只看大厂背景），没项目的 Leader 带不了新人 | LinkedIn、脉脉、面试时反问 |
| **方向是否主流** | 大模型应用开发 / RAG / Agent / AI 办公 / AI 客服 / AI 销售 / AI 教育 / AI 数据分析 / 行业数字化工具 / 企业支付——越靠近 AI 应用层越适合 AI PM 应届生入行 | 官网产品页、行业报告 |

**输出格式**：一页"公司评估简报"——4 个维度各一句话 + 风险提示 + 面试时建议反问 Leader 的问题。

### 4.6 JD 解析子模块

#### 用户故事

> **作为** 求职者，**我希望** 把任意格式的 JD（大厂校招、初创口语文案、英文 JD）粘贴进去，Agent 能提取出结构化的岗位画像，**以便** 我不需要自己从一大段文字里判断"这个岗位到底在招什么人"。

**验收标准**：
- 输入一份 JD 文本（≥ 30 字），输出 `JobDescription` Pydantic 对象
- 区分硬性要求（must_have）和加分项（nice_to_have），准确率 ≥ 90%
- 支持 JD 长度从 30 字到 3,000 字
- 信息不足时标注 `info_sufficient=False`，而非静默返回空字段

#### 输入/输出

```
输入：JD 纯文本 / URL（联网抓取）
  ↓
JD 解析器（LLM + Pydantic 校验）
  ↓
输出：JobDescription {
  company: str,             # 公司名
  role: str,                # 岗位名
  location: str,            # 地点
  summary: str,             # 一句话岗位画像
  responsibilities: [str],  # 岗位职责
  requirements: [           # 任职要求（区分硬性/加分）
    {content, type: must_have|nice_to_have, category}
  ],
  raw_text: str,            # 原始文本
  info_sufficient: bool     # 信息是否足够分析
}
```

#### 与简历解析的关键差异

| 维度 | 简历 | JD |
|------|------|-----|
| **文本性质** | 事实陈述——"我做了什么" | 营销文案——"我们想要什么" + "我们多厉害" |
| **语言风格** | 相对标准化（教育、技能、项目） | 高度不统一——大厂正式、初创口语、外企中英混杂 |
| **隐含信息** | 少——简历写什么就是什么 | 多——"能承担压力" = 加班、"扁平化管理" = 没有晋升通道 |
| **结构可预期性** | 高——90% 的简历有"教育/技能/项目" | 低——有的叫"任职要求"、有的叫"我们需要你"、有的直接一段话 |
| **LLM 的挑战** | 提取 + 归纳 | 提取 + 翻译（把营销语言翻译成结构化要求）+ 去噪音 |

**核心差异一句话**：简历解析是"信息提取"，JD 解析是"信息提取 + 营销语言翻译"。

#### 风险点

| # | 风险 | 典型表现 | 应对 |
|---|------|---------|------|
| R-JD1 | **JD 过于口语化** | 初创公司 JD："我们是一群想改变世界的人，希望你也有点疯狂"——几乎没有可提取的硬技能要求 | 标注 `info_sufficient=False`，提示用户"这个 JD 信息不足，建议找更详细的版本或直接联系对方" |
| R-JD2 | **硬性 vs 加分边界模糊** | JD 写"熟悉 Python"——是必须会还是加分？LLM 无法可靠判断 | 默认标注为 must_have（宁可严格不宽松），置信度降为 medium |
| R-JD3 | **中英混杂** | 外企 JD："要求熟悉 LLM application development，有 production deployment 经验" | Prompt 明确要求保留原文措辞；requirements 的 content 字段保留混搭语言 |
| R-JD4 | **JD 过长/过短** | 过短：30 字一句口号；过长：大厂 JD 含公司介绍、福利、团队介绍等非需求内容 | 过长 → LLM 自动去噪（只提取职责+要求）；过短 → info_sufficient=False |
| R-JD5 | **隐含/黑话翻译不准** | "我们希望你皮实" → 是抗压能力，LLM 可能不理解 | 在 Prompt 中列出常见互联网黑话对照表（见下方） |

**常见 JD 黑话对照表**（Prompt 内置）：

| JD 原文 | 实际含义 |
|---------|---------|
| "能承担压力"、"皮实" | 加班较多，需要抗压能力 |
| "扁平化管理" | 公司规模小，管理层级少（也可能是管理混乱） |
| "薪资 open"、"上不封顶" | 薪资结构偏绩效，底薪可能不高 |
| "希望你快速成长" | 入职即上手，培训资源有限 |
| "有创业精神" | 需要你身兼多职，职责范围不固定 |
| "我们是一家人" | 边界感弱，可能需要非工作时间响应 |

### 5.1 系统性质

**CareerMatch Agent 是基于 LLM 的概率性系统**，不是确定性规则引擎。

这意味着：
- 同一份 JD + 同一份简历，两次分析可能给出 95 和 91 的评分差异
- 匹配结论是"高置信度建议"，不是"绝对真理"
- 最终决策者永远是**用户本人**，Agent 只负责提供结构化参考

### 5.2 准确率目标

| 指标 | 目标值 | 测量方法 |
|------|--------|---------|
| 匹配度评分偏差 | ≤ ±5 分（同一份 JD-简历对，3 次重复测试） | 标准差 |
| 匹配维度判断准确率 | ≥ 90%（与人工标注对比） | LLM-as-a-Judge + 人工抽检 |
| 简历建议采纳率 | ≥ 70% 用户自评"建议有效" | 用户反馈 |
| 面试题覆盖度 | ≥ 60% 面试后"确实被问到了" | 面试后回访 |

### 5.3 已知边界（v0 诚实声明）

| 能做 | 不能做 |
|------|--------|
| 匹配 JD 中的硬技能关键词 | 判断你的真实技术水平（你说会 Python，Agent 默认你会） |
| 分析 JD 文本本身 | 判断 JD 是否真实（挂羊头卖狗肉的岗） |
| 基于公开信息评估公司 | 了解公司内部真实情况（政治、加班、离职率） |
| 预测常见面试题 | 预测某个面试官的个人偏好 |

### 5.4 失败模式与兜底

| 失败模式 | 表现 | 兜底策略 |
|----------|------|---------|
| **JD 太模糊** | JD 全是"负责产品规划"这种空话，Agent 无法提取有效信息 | 提示用户"这个 JD 信息量不足，分析结果仅供参考，建议找更详细的版本" |
| **简历太薄** | 课程项目一句话带过，没有可分析的细节 | 提示用户"简历信息太少，建议先补充项目细节再分析" |
| **领域过于垂直** | JD 涉及很窄的行业知识（如量化金融、芯片设计） | 标注"低置信度"，建议用户自行判断行业特定维度 |
| **LLM 幻觉** | 分析引用了 JD 中不存在的技能 | Pydantic 校验层会要求引用 JD 原文作为证据，无原文支撑 → 降置信度 |

## 6. 模型选型

### 6.1 角色分工

```
┌──────────────────────────────────────┐
│            CareerMatch Agent          │
│                                       │
│   ┌─────────────┐   ┌─────────────┐  │
│   │  主力模型     │   │  Judge 模型  │  │
│   │  负责执行     │   │  负责评估    │  │
│   │  分析·生成   │   │  打分·校验   │  │
│   └─────────────┘   └─────────────┘  │
└──────────────────────────────────────┘
```

### 6.2 主力模型：DeepSeek V4 Pro

| 维度 | 评估 |
|------|------|
| **模型** | `deepseek-chat`（V4 Pro，OpenAI 兼容接口） |
| **中文能力** | 第一梯队——JD 和简历都是中文场景，中文理解不能打折 |
| **性价比** | 输入 ¥1/1M tokens，输出 ¥2/1M tokens，单次分析约 ¥0.05 |
| **Function Calling** | 支持，用于 Agent 工具调用 |
| **结构化输出** | 通过 prompt 约束 + Pydantic 校验实现 |
| **选型理由** | 三项均衡——中文能力 ≥ GPT-4o、成本 ≈ GPT-4o 的 1/10、响应速度 < 5s |

### 6.3 Judge 模型：DeepSeek Reasoner

| 维度 | 评估 |
|------|------|
| **模型** | `deepseek-reasoner`（推理增强） |
| **用途** | 评估主力模型的输出质量——匹配维度判断是否合理、建议是否可操作 |
| **使用频率** | 每 3 次分析调用 1 次 Judge 复核；此外用于新版本上线前回归测试 + 疑难 Case 仲裁 |
| **选型理由** | Reasoner 有推理链，评估时能给出"为什么这个匹配判断是错的"，比只给一个分数的 Judge 更有调试价值 |

### 6.4 备选方案（暂不使用，记录备查）

| 模型 | 不选的理由 |
|------|-----------|
| GPT-4o | 成本高 10 倍，中文场景无明显优势 |
| Claude 4 Sonnet | 成本高，且目前内置 Agent 工具链主要适配 OpenAI 兼容接口 |
| 本地模型（Ollama/Qwen） | 部署复杂度高，Function Calling 不稳定，不适合 21 天快速上线 |

### 6.5 模型切换原则

如果 DeepSeek 服务不稳定（大规模故障 / 响应超时 > 10s 持续 1 小时以上），保留一键切换到 OpenAI 兼容备选的能力——`src/config.py` 改两行即可。

## 7. Agent 设计

### 7.1 为什么是 Agent 而不是固定 Workflow

固定 Workflow 是这样：

```
JD → 技能提取 → 简历 → 技能提取 → 逐项比对 → 输出
```

这条流水线对"标准 JD"有效，但现实中的 JD 千差万别：

| JD 类型 | Workflow 翻车表现 | Agent 怎么做 |
|---------|-------------------|-------------|
| **极简 JD**（3 句话："招 AI PM，负责产品规划"） | 技能提取不到东西，匹配维度全空 | Agent 先判断"信息不足"→ 联网搜索该公司其他 JD → 补全画像 → 标注低置信度 |
| **技术 JD**（全是技术栈名：LangChain/向量库/RAG） | 技能匹配全是"不匹配"，给不出有用建议 | Agent 先翻译术语 → 识别哪些是"学了就会的"vs"需要经验的"→ 分层建议 |
| **外包/假 JD** | 正常比对了，但公司本身有问题 | Agent 先跑公司评估 → 发现"18 个月没融资"→ 标记风险，再做匹配 |
| **大厂校招 JD**（标准化、信息完整） | Workflow 够用 | Agent 跳过信息补全步骤，直接进入匹配 + 面试题预测 |

**核心差异**：Workflow 只有一条固定路径。Agent 能**先判断再行动**——信息不全先去搜、公司可疑先去查、JD 技术术语太多先翻译。

### 7.2 Agent 决策循环

```
┌──────────────────────────────────────────┐
│  Agent 决策循环（ReAct 模式）              │
│                                          │
│  ┌──────────┐    ┌──────────┐           │
│  │ Think    │ ←→ │ Act      │           │
│  │ 我该做什么 │    │ 调用工具  │           │
│  └────┬─────┘    └────┬─────┘           │
│       │               │                  │
│       ▼               ▼                  │
│  ┌──────────┐    ┌──────────┐           │
│  │ Observe  │ ←─ │ Tool     │           │
│  │ 分析结果  │    │ Result   │           │
│  └────┬─────┘    └──────────┘           │
│       │                                  │
│       ▼                                  │
│  ┌──────────┐                           │
│  │ Decide   │  下一步做什么？             │
│  │ 继续/完成 │  信息够了 → 输出报告        │
│  └──────────┘  不够 → 回到 Think         │
└──────────────────────────────────────────┘
```

### 7.3 Agent 工具集（7 个工具）

| # | 工具名 | 功能 | 触发条件 | 对应需求 |
|---|--------|------|---------|---------|
| T1 | `translate_jd` | 把 JD 术语翻译成人话，输出"岗位画像" | 所有分析的第一步 | US-01 看懂 JD |
| T2 | `match_skills` | 简历 ↔ JD 的 8 维度匹配，每维标注证据 | translate_jd 完成后 | US-02 诚实匹配 |
| T3 | `evaluate_company` | PMF/融资/Leader/方向 四维评估 | 公司名可识别时 | US-02（公司维度） |
| T4 | `web_search` | 联网补全公司信息、JD 上下文 | 信息不足时触发 | T1/T3 的辅助 |
| T5 | `suggest_resume_fix` | 针对差距给具体修改建议（定位→问题→改法→示例） | match_skills 发现不匹配时 | US-03 改简历 |
| T6 | `predict_interview_qs` | 基于 JD + 差距生成 5 道面试题 + 答法要点 | 匹配报告完成后 | US-05 押面试题 |
| T7 | `generate_cover_letter` | 生成 ≤300 字个性化求职信 | 用户主动请求时 | US-04（P2） |

### 7.4 典型分析路径

```
路径 A：标准分析（大部分情况）
T1 → T2 → T5 → T6
（翻译 → 匹配 → 改简历 → 押题）

路径 B：信息不足时的分析
T1 → T4(补全) → T2 → T3 → T5 → T6
（翻译 → 搜索补全 → 匹配 → 公司评估 → 改简历 → 押题）

路径 C：可疑公司检测
T1 → T3(先查公司) → 高风险？→ 警告 + 是否继续
                         → 低风险？→ T2 → T5 → T6
```

### 7.5 输出校验层

Agent 所有输出必须经过两层校验，再展示给用户：

| 层 | 校验对象 | 规则 |
|----|---------|------|
| **Pydantic Schema** | 字段类型、必填项 | 匹配维度必须有 ≥ 5 个非空 + 每维有证据 |
| **置信度标注** | 输出质量 | 信息不足的维度 → 标注"低置信度"；LLM 推断的内容 → 标注"推测" |
| **敏感信息过滤** | 安全 | 联网搜索结果不直接展示原始内容，只展示 Agent 摘要 |

## 8. 评估方案

### 8.1 测试集设计

| 类别 | 数量 | 说明 | 示例 |
|------|------|------|------|
| **Happy Case** | 15 条 | 标准 JD，信息完整，JD 与简历方向匹配 | 大厂校招 AI PM、AI 产品运营 |
| **Edge Case** | 10 条 | 边界情况——JD 极简（<50 字）、技术术语过多但本质是 PM 岗、JD 描述模糊全是空话 | "招 AI PM，负责产品"（10 个字）、JD 列了 20 个技术栈但岗位是 PM |
| **Adversarial** | 5 条 | 对抗样本——JD 含明显矛盾（岗位职责与要求不匹配）、疑似虚假 JD、非 AI 方向的误导性 JD | "AI PM 岗，要求管理 50 人团队"、外包套皮 JD、非 AI 公司挂 AI 名头的 JD |

**总计 30 条测试 JD**，覆盖真实求职中能遇到的典型和极端场景。

### 8.2 评估方法：LLM-as-a-Judge

```
主力模型生成报告 → Judge 模型（deepseek-reasoner）打分 → 人工抽检 20%
```

| 维度 | 权重 | 评分标准 |
|------|------|---------|
| **匹配准确性** | 30% | 技能/经验/学历判断是否合理，与人工标注一致 |
| **建议可操作性** | 25% | 修改建议是否具体到行、可执行 |
| **JD 理解正确率** | 20% | 术语翻译是否正确、岗位画像是否准确 |
| **输出完整性** | 15% | 必含模块不缺，格式一致 |
| **公司评估合理性** | 10% | 风险评估是否客观、数据来源是否标注 |

### 8.3 评估流程

```
每次 Agent 改版后执行：
1. 跑 30 条测试 JD（用同一份固定简历）
2. Judge 模型逐条打分（5 维度）
3. 计算加权总分
4. 人工抽检 6 条（20%）验证 Judge 是否公允
5. 判定：总分 ≥ 90% → 通过
         总分 80-90% → 通过但需修复
         总分 < 80% → 不通过，回退
```

### 8.4 评估记录

所有评估结果记录到 `docs/EVALUATION.md`，格式见该文件模板。每次评估生成一个版本号（如 v0.1-eval-1），便于对比迭代前后的效果变化。

## 9. 成本估算

### 9.1 单次分析 Token 消耗

以路径 A（标准分析：T1 → T2 → T5 → T6）为例：

| 步骤 | 说明 | 输入 tokens | 输出 tokens |
|------|------|------------|------------|
| T1 `translate_jd` | JD 翻译 + 岗位画像 | ~800 | ~300 |
| T2 `match_skills` | 简历 ↔ JD 8 维匹配 | ~2,500 | ~1,200 |
| T5 `suggest_resume_fix` | 简历修改建议 | ~1,000 | ~800 |
| T6 `predict_interview_qs` | 5 道面试题 + 答法 | ~1,000 | ~800 |
| — | System Prompt + Agent 调度 | ~800 | ~200 |
| **小计** | | **~6,100** | **~3,300** |

路径 B（含联网搜索 + 公司评估）增加约 2,000-3,000 input tokens。

### 9.2 主力模型成本（deepseek-chat）

```
输入：¥1 / 1M tokens
输出：¥2 / 1M tokens

单次标准分析 = (6,100 / 1,000,000) × 1 + (3,300 / 1,000,000) × 2
             = 0.0061 + 0.0066
             = ¥0.0127
             ≈ ¥0.01
```

### 9.3 Judge 模型成本（deepseek-reasoner，每 3 次调用 1 次）

```
输入：约 ¥4 / 1M tokens
输出：约 ¥16 / 1M tokens

单次 Judge = (2,000 / 1,000,000) × 4 + (500 / 1,000,000) × 16
           = 0.008 + 0.008
           = ¥0.016

分摊到每次分析 = ¥0.016 / 3 ≈ ¥0.005
```

### 9.4 综合成本

| 场景 | 每次成本 | 100 次 | 1,000 次 |
|------|---------|--------|---------|
| 标准分析 + 每 3 次 Judge | **≈ ¥0.02** | ¥2 | ¥20 |
| 含联网搜索 + 公司评估 | **≈ ¥0.03** | ¥3 | ¥30 |

### 9.5 参考对比

| 方案 | 每次成本 | 1,000 次 |
|------|---------|---------|
| DeepSeek（主力 + Judge 分摊） | ¥0.02 | ¥20 |
| GPT-4o（同等 token 量） | ~¥0.15 | ¥150 |
| 人工修改简历（1 次） | ¥0 | — |

**21 天开发期间，全部调用成本预计 < ¥50。**

## 11. Web 前端与部署方案

### 11.1 技术选型：Streamlit vs React

| 维度 | Streamlit | React (Vite/Next.js) |
|------|-----------|---------------------|
| **开发速度** | 1-2 天可完成 MVP 界面 | 至少 5-7 天（组件+状态+路由+样式） |
| **技术栈** | 纯 Python，零前端代码 | TypeScript + CSS + API 对接 |
| **学习成本** | 无（Python 开发者即写即用） | 需掌握 React 生态（hooks/state/路由） |
| **UI 灵活性** | 受限于 Streamlit 组件库 | 完全自定义 |
| **状态管理** | 自动（session_state） | 需手动管理（useState/useReducer） |
| **部署复杂度** | `streamlit run app.py` 一条命令 | 需构建 + 静态托管或 Node 服务器 |
| **响应式** | 自带基础响应式 | 需手写 CSS media queries |
| **适合场景** | 数据/ML Demo、内部工具、快速原型 | 面向消费者的产品、复杂交互 |

#### 选型结论：Streamlit

**理由**——按优先级排列：

1. **时间约束。** 21 天排期中，前端+部署共 3 天（Day 17-19）。Streamlit 1 天写完界面 + 1 天打磨 + 1 天部署，刚好够。React 至少需要 5-7 天，挤占评估迭代的时间。

2. **开发者的比较优势。** 我是 PM，不是前端工程师。Streamlit 的 `st.text_area()` + `st.file_uploader()` + `st.markdown()` 就够用，不涉及 CSS/JS。省下的时间用来打磨分析质量——这是产品的核心价值。

3. **MVP 阶段不需要自定义 UI。** v0 用户是我自己 + 30 个同学，不是面向公众的 SaaS 产品。Streamlit 的默认布局（单列 + 侧栏）足够清晰，不需要品牌化设计。

4. **单一代码库。** 整个产品（解析→Agent→渲染→UI）都在 Python 中，不需要 API 边界、不需要前后端联调、不需要处理 CORS。

5. **Streamlit 的局限在 v0 不构成瓶颈。** 已知限制：不支持多页面路由、自定义 CSS 有限、不支持 WebSocket 实时推送。对于 v0——一个"粘贴 JD + 上传简历 → 看报告"的单页工具——这些都不需要。

> **未来迁移路径**：如果 v1 需要更复杂的交互（如多轮对话式分析、实时流式输出报告），可以考虑用 FastAPI + React 重写前端。但 v0 的 Streamlit 代码不会浪费——所有业务逻辑（解析器/Agent/渲染器）独立于 UI 层，迁移时只需改 `app.py` 的调用方式。

**关键设计决策：**

- **分析前先展示解析结果。** 在"开始分析"按钮上方，实时预览解析后的简历摘要（姓名/教育/技能数/项目数）和 JD 摘要（公司/岗位/要求数）。用户确认信息正确后再启动分析——避免"跑了 50 秒发现简历解析错了"。
- **分析过程透明。** 每完成一个工具调用，页面更新一条状态。让用户知道"正在做什么"而不是干等 50 秒。
- **报告页不跳转。** 分析完成后在当前页面显示报告，不跳转到新页面。用户可以在报告上方看到自己的输入，方便对照修改。

### 11.5 `app.py` 架构概览

```python
# 伪代码——实现时以此为骨架

def main():
    st.title("CareerMatch Agent")

    col1, col2 = st.columns(2)
    with col1:
        pdf_file = st.file_uploader("上传简历", type=["pdf"])
        if pdf_file:
            resume = parse_resume(pdf_file)
            st.info(f"{resume.name} | {resume.education[0].school}")

    with col2:
        jd_text = st.text_area("粘贴 JD", height=200)
        if jd_text.strip():
            jd = parse_jd(jd_text)
            st.info(f"{jd.company} | {jd.role}")

    want_cover = st.checkbox("生成求职信")

    if st.button("开始分析", disabled=not ready):
        with st.status("分析中...") as status:
            engine = AgentEngine(resume, jd, user_wants_cover_letter=want_cover)
            report, trace = engine.run()
            # 每步更新 status

        md = render_report(report)
        st.markdown(md)
        st.download_button("下载报告", md, file_name=f"report_{jd.company}.md")
```

**关键约束：**
- `app.py` 只做 UI 编排，不包含任何业务逻辑
- 所有分析逻辑走 `src/` 模块（parsers → Agent → renderer）
- 错误处理：每个 `try/except` 给出对用户友好的中文提示，不展示 traceback
